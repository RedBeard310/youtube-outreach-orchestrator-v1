The three questions

Q1Why did nobody get an email on a sending Thursday?

The send program quit on the first of its six steps, and that step does not send anything. The timer fired correctly. siege-plan.service started at 11:15:02Z and the whole run ended on the one line it wrote to the system journal: 

Nov 19 11:15:02  python3[3690549]: INBOX_KIT_API is not set (expected in env-storage/.env)

That is inbox-warmup-sync.py, the first step. Its only job is to download how old each sending mailbox is and how its warmup is going, and save that to a file the planner reads later. The send day is built as one chain of six commands that run in order, and the system abandons every remaining command the moment one of them fails. So the five behind it never ran: the campaign enrolment, the 20 sample emails, the approval record, the live push, and the report. There is no state/siege/2026-11-19 folder on disk at all.

The key was there the next morning. INBOX_KIT_API is in the shared settings file right now, so nothing was deleted. What happened is a race: Casey’s Mac rewrites that file on the VPS about every two minutes, and the reader walks it one line at a time with no check that it got the whole thing, so a file caught halfway through being written loads as a short file and reports no error. A one-second overlap took the sending day.

The watchdog did its job. The hourly check wrote siege_send_day_failed at 12:11:02Z, 56 minutes after the crash. Siege stops pushing at noon New York time, so roughly five hours of sending day were still recoverable at that point. Nothing acted on it, which is expected: the loop runs unattended and the repair is in automator, a repo the self-improvement agent is not allowed to edit.

Q2Why did the snapshot blame the timer?

Because the one field a reader opens first had no name for this, so it borrowed the name next to it. binding_constraint published plan_missing_on_sending_day, whose own written meaning is that the day produced no plan and the timer is what to look at. The timer was flawless.

Three names already existed for a send program that failed: unit_died_before_push, push_unit_failed and push_killed. None of the three could be reached on Thursday, and not by accident. All three sit behind a test for “a plan that moved nothing”, that test needs to know how many people were planned, and that number comes from the plan file. No plan file, no number, no branch. The one shape where the crash comes first is the one shape the crash names could never describe.

This is the same fault as 2026-10-29, when a plan that held nobody fell through every branch and printed nothing at all, and the same as 2026-10-30, when a crashed program borrowed the name of an approval wait that cannot happen any more. Each time it lands in the field a tired reader checks before any other. Fixed this morning, see below.

Fixes shipped this cycle

A send day lost to a crash read as a timer that never fired

53ecfe9fd, youtube-outreach-orchestrator-v1

Q2 is the whole story, and it is the one thing this cycle could close. Two changes, both to the reporting, because the crash itself is in automator.

The headline field now names the crash. No plan on a sending day plus a send program that ran inside this cycle and failed now reads unit_died_before_plan instead of plan_missing_on_sending_day. The verdict it reads was already scoped to this cycle by existing code, so a failure left over from Friday cannot rename a Sunday. A missing verdict and a verdict of success both keep the old name, because an unmeasured program is unknown and a program that reported success and still wrote no plan really is the timer’s question.

The hourly alarm can now name the first step. It read step: unknown on Thursday, which says only that no state folder exists, about a run whose cause was one line away. The first step answers for itself for free, on the same principle the two rungs below it already use: a step that finished left a file behind. inbox-warmup-sync.py rewrites state/inbox-warmup.json and stamps it, and it refuses to overwrite a good file with an empty one, so a stamp older than the run’s own start means that step did not finish. Thursday read 2026-11-18T11:15:15Z against a run that started 2026-11-19T11:15:02Z. A day stale, unmistakable, and nothing was reading it. The new warmup rung says the cause is a missing or momentarily unreadable credential and not a crash inside Siege, which is a different repair.

Both only ever claim what they measured. An unreadable or absent warmup file falls through to unknown rather than blaming the first step, which is the rule every other rung here follows and the one the 10-29 and 10-30 faults came from breaking. The alarm also stopped describing the chain as five steps; it is six, and only the campaign enrolment is allowed to fail without taking the day.

Verified: the self-test suite passes in full with 11 new assertions, including every way both changes must stay silent, and both files typecheck clean. The crash, its timestamp, the missing state folder, the stale warmup stamp and the alarm firing at 12:11:02Z were all read out of the live journal, the live disk and the live observation log before anything was written.

What to do next

  1. Stop the warmup step being able to cost a sending day. New this cycle and the single highest-value thing on this list. The step downloads a report; it writes no email and sends nothing, and losing it costs the planner slightly stale mailbox ages. It does not justify cancelling the four steps behind it. Two options, either is enough: put a leading - on that one ExecStart line in siege-plan.service, the way the campaign enrolment line already has, or make the settings reader refuse a half-written file instead of silently loading a short one. The second also protects every other script that reads that file. Both live in automator, which the autopilot may not edit, so this is yours.
  2. Decide what the slots are for. Unchanged for eleven days and still the biggest outbound lever. Thursday is a gap in the evidence rather than a new data point, but the eight days around it reached 13 people for the first time while 4,853 finished emails sit on the shelf. The whale tier finished its never-emailed book on 2026-10-13 and its repeat-offer queue still takes slots ahead of ready lower-tier people. The lever is siege.fill_slots and its priority_key, in automator. Repeat offers were your call on 2026-10-07, so the mix is yours to set.
  3. Replace the Apify token. Eight days now, 191.6 hours with no work done, 10 refused ticks on the current run, $21.06 of allowance that expires 2026-11-30. Still HTTP 401 user-or-token-not-found. Operator-only, so nothing here can do it. Unchanged from the last six mornings.
  4. Watch the fleet on Friday, and decide nothing yet. Ten clear mailboxes lost with zero returned is the sharpest one-day fall in three weeks, but Thursday sent no email at all, so none of it was earned by Thursday’s own sending. Nine of the held mailboxes are already healthy, six on a clock with the soonest owing one hour, so part of it lifts by itself. One more morning says whether this is a slide or a wobble.
  5. Nothing needs doing about the recovery lane, the enrichment chain, the reply lane or the keys.
