What broke, what's fixed

1. A quiet Saturday and a broken Monday produced the same snapshot

Fixed: youtube-outreach-orchestrator-v1 a709b598. Nothing for Casey to do.

This was the first weekend the send-plan block has had to describe. It emitted plan_found: false, planned: null, binding_constraint: null and nulls for everything else. That is also, exactly, what a Monday whose timer never fired would emit. One of those days is correct and expected. The other is a whole sending day gone, 200 emails not written, with no error line anywhere in the system to find it by. A report that cannot tell them apart will eventually call the bad one fine, because ten weekends of practice will have taught everyone that the shape is harmless.

So the block now asks the timer what days it runs on. Three things come out of that:

A verdict instead of a silence. binding_constraint says not_a_sending_day when the calendar excludes the day, and plan_missing_on_sending_day when it doesn't. Both cases used to produce null, which reads as "no finding". The second one is now the loudest thing in the block. A batch driven by hand no longer covers for a missing plan either: that used to come out as partial_push, which claims a plan moved part of itself.

The schedule is read, not remembered. The weekday rule comes from the timer's own OnCalendar line. Writing Mon..Fri into the gatherer would have been one line shorter and would have gone stale: that schedule already moved once, from 08:15 to 06:15 on 10-01.

The unit now reports on itself. unit_state, unit_last_result and unit_last_started carry Siege's most recent run whenever it happened, so yesterday's "go and look at systemctl status after Monday" is answerable from the snapshot. It is deliberately separate from the existing push_unit_result, which stays null unless that run happened inside the cycle, because a Friday verdict must never be printed as a Saturday outcome.

Verified: typecheck clean, the gatherer's self-test passes with 14 new cases (comma lists, a range that wraps past Sunday, a calendar with no weekday field, and an unknown abbreviation refusing to guess), and run against live systemd: Friday 10-02 true, Saturday 10-03 false, Sunday 10-04 false, Monday 10-05 true. Today's snapshot now reads binding_constraint: not_a_sending_day with push_unit_result still correctly null.

2. The same code read systemd's answers by position, and was right by luck

Fixed: same commit.

The existing probe asked systemd for two properties and then took the answers in the order it had asked for them. systemd prints properties in its own fixed order and ignores the order of the request. For these two it happens to agree, so the code worked, and it would have kept working right up until somebody added a third property or a systemd release reordered them.

The failure it was one edit away from is specific and familiar. The timestamp would have landed in the slot holding the result, every push verdict would have gone to null, and a killed push would have been reported as partial_push, meaning "a few leads the builder couldn't finish". That is precisely the wrong diagnosis the 10-02 and 10-03 debriefs spent two days undoing. Properties are now read by name.

3. The parked pool overstates what is left to email, by 548 and growing

Measured, not fixed. No code change needed, just a number to read correctly.

The pool figure at the top of every one of these reports counts everything in approved_hold, and sending an email does not take a lead out of approved_hold. So the 7,591 includes people who have already been written to. Queried today: 7,033 of the shelf sit at ready_data_scraped and 548 sit at sent_to_smartlead. Those 548 are the cumulative output of the send path to date, and the first time this series has been able to state it as one number.

It matters because of the arithmetic it changes. The ramp is at 200 a day across four delivery days, so a full week consumes roughly 800 of the 7,033, while the only lane still adding leads contributed 2. At that pace the inventory is about nine weeks of email, and the headline pool number will keep drifting further above the real figure every day the send runs. 7,033 is the number to watch from here, not 7,591.
