The three questions

Q1Why did the pipeline park only 2 leads?

The finder had nothing to search for. Every session's reservoir check returned STOCK-UP · fresh 0 · need 48 — the fresh-term pool is empty. The two refuel paths both dead-end: (a) the keyword harvest that pulls real autocomplete tails is correctly skipped because the endpoint is IP-blocking us (sustained HTTP 403); (b) the LLM discovery fallback invents 40 frontier veins each pass but every one dedupes to 0 against the 7,054-term table — the generator has no fresh signal to diverge from, so it reconverges on ground already mined. With no active terms, the finder aborts, two aborts trip the hard-wall, and the session parks 0. That happened 44 times in a row.

The 4 pitchable that did surface (2 Financial Planning, 1 Real Estate, 1 Legal) came from a single pass that caught a sliver of residual supply. 2 had verifiable emails → parked. That's the whole cycle.

Q2Why has this run for 10 days without self-healing?

Because the fix isn't in code — it's the network path. The block is an IP-reputation 403 on Google/YouTube's public suggest endpoint: our datacenter egress IP is denied. The finder's circuit-breaker, the campaign's harvest-skip, and the check-in's backstop all detect it correctly and stop hammering it — which is right (hammering deepens the block) but means the loop can only wait. The one thing that reopens supply is an infra change: rotate the egress IP or route the harvest through a residential/proxy path. No agent in the loop can do that (it touches host networking, which is operator-owned).

The gap this exposes: the autopilot has no soft-alert channel. Its only escalation is the halt flag, which stops everything — wrong for a supply block where the parked inventory is fine and should keep being worked. So a 10-day block stayed visible only in these daily debriefs, never surfaced as "go rotate the IP."

Q3Is anything actually broken — or is the system behaving correctly?

Mostly behaving correctly. Under a total supply block the autopilot did the safe things: harvest skipped 47× (never stormed the 403 endpoint), the finder aborted before any search.list call so zero YouTube quota was burned (quota_stops: 0), the loop backed off ~30 min per hard-stop instead of thrashing (contrast 2026-07-13's 168× at 2.5-min intervals), Anthropic burn was $0, and the check-in raised no fatal signatures. Nothing needs a human to unstick the machine.

And the thing that looks like waste already isn't: the LLM discovery fallback's claude-sonnet-5 generation was suppressed on 40 of 50 discovery calls this cycle by the finder's own TTL dry-guard (shipped 2026-07-14). Only 10 leaked through — one per ~3h re-arm probe, deliberate so a frozen table can't deadlock the finder forever. That's pennies/day and it self-heals. A redundant campaign-layer backoff was drafted this cycle, checked against the logs, found redundant + interaction-defective, and reverted (see below).

Recommended next — ranked

  1. Rotate the egress IP / proxy the autocomplete harvest (INFRA — operator only, unblocks everything). This is the single action that restarts fresh finding. Ten days blocked; every other lever below is downstream of it. Nothing in the autonomous loop can do this — it's host networking. Until it's done, fresh supply stays at ~0/day.
  2. The needs_contact recovery engine — now the highest-value unblocked lever. 3,685 found-and-scored creators sit parked with no verified email. Recovering even 30% (~1,100) dwarfs weeks of blocked fresh-finding — and it needs no new finding, so it sidesteps the autocomplete block entirely. With supply dead for 10 days, this is where the next real volume comes from. Deferred, awaiting greenlight.
  3. A non-halting escalation channel for the autopilot. Today's block would have warranted a "supply blocked N days — rotate the IP" nudge on day 1, not a silent 10-day wait broken only by these debriefs. A lightweight alert (append to a watched file / a single ping) for the "fresh_finding_dead ≥ N cycles" shape, distinct from the halt flag, would close the visibility gap Q2 exposed — but only if wired to something you actually watch (the loop has no external notify path today, so this is a design task, not a quick code drop).

Self-improvement this cycle: none — deliberately

I drafted one candidate — a campaign-layer dry-streak backoff to stop re-paying the discovery sonnet-5 call during a saturated-table drought — then checked it against the actual cycle logs before trusting it. Ground truth killed it: the finder's existing 07-14 TTL dry-guard already suppresses 40 of 50 discovery calls, and the campaign guard's fail-open parse treats a finder "went dry" skip as productive, so its streak would reset on ~80% of sessions and it would almost never engage — a redundant second guard with real interaction risk for pennies/day. I reverted it. Every cheap durable fix has already landed across the 10-day block (circuit-breaker → block-aware harvest → block-backoff → dry-guard → +19 verticals → supply_health feed → fresh_finding_dead grounding → benign-hard-wall suppression), each buying less. The binding constraint is 100% infra plus the unbuilt needs_contact engine. Per the debrief rule — no high-confidence improvement ⇒ ship nothing, don't invent churn.
