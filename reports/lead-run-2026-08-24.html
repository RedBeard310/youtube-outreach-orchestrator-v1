The three questions

Q1Where did 189 parked leads come from?

Mostly from creators we found weeks ago and wrote off. Casey merged the recovery lane at 21:27Z last night. It works the needs_contact pool: people who clearly fit, who we located and scored, but whose email we could never confirm. Until now nothing touched that pool. It had been sitting since a single hand-run on 08-18.

Counting it three ways gives the same answer. 84 leads now sitting in approved_hold carry an email the recovery tool dug up and had touched inside this cycle. The merge commit records 70 flips from the hand-run that shipped it. The scheduled lane's own first pass added 7 more. So call it roughly 77 to 84 of the 189, with the rest, about 110, coming from the normal find-then-verify path, which is a perfectly ordinary day by itself.

Why this is the interesting number and not just a good one: those 77 leads cost nothing to find. The finding was paid for weeks ago and written off. That is the whole reason cost per parked lead fell from 7.5¢ to 4.2¢ while cost per lead found barely moved. Recovery is not a new supply of creators. It is a second pass over supply already bought.

One number to keep honest: needs_contact still grew, 4,241 to 4,345, because the day's finding swept 172 fresh unreachable creators in while recovery pulled fewer out. The pool is not shrinking yet.

Q2Is the top lane slowing down, like the snapshot says?

No. It sped up 15.8%, and the −31% in the snapshot is the last echo of the bug fixed last night.

The snapshot compares today's 8,710 seeds against yesterday's stored figure of 12,647. That stored figure is the old double-counted log sum, written before the fix landed. Yesterday's debrief established the true number was 7,523. Against that, today is up 15.8%.

The guard built last night did its job. It reports the percentage, because the arithmetic is honest as far as it goes, but it refuses to escalate when the two sides were measured differently: throughput_bound came back null rather than true. Without that guard this debrief would be leading with a second phantom regression in three days. Tomorrow both sides are book deltas and the flag arms itself again.

Q3Did the new recovery lane spend its money well?

No. It paid to check the same dead addresses twice on its first night, and left alone it would have done that forever.

The lane runs a verify pass every three hours. It picks creators who have an email address on file that nobody has confirmed yet, and pays a small credit to ask whether that address is real. Both passes ran:

Pass 1 (23:30Z)Pass 2 (02:40Z)
Leads selected9184

The three identical numbers are the giveaway. Pass two re-selected 84 of the same 91 people, re-rejected the same 83 addresses, re-checked the same 33 dead ones, and flipped nobody.

The cause is one word doing two jobs. A contact address carries a flag, verified. The recovery tool sets it to false when an address has not been checked yet. It also sets it to false when the address has been checked and came back dead, and again when the address turns out to belong to a stranger rather than the creator. So "false" means both "still to do" and "already ruled out", and the lane's selector read every one of them as work waiting.

What it was costing. Eight passes a day at roughly 34 wasted credits each is about 270 credits a day, indefinitely, for a guaranteed zero. Measured on the live database this morning, the selector returned 85 leads of which 83 had already been ruled on, and 83 address records had already collected the same rejection note more than once after only two passes. Ninety-eight percent of the lane's paid work was repeat work, on night one.

Shipped today

Four commits across three repos. Every one verified against live state before committing. Nothing in any .env.

1. The recovery lane stops re-checking addresses it already ruled dead

src/recovery/bloodhound-lane.ts in the orchestrator, commit d6af815. This is the Q3 fix.

The selector now skips any address carrying either mark the tool already writes: a timestamp saying the credit was spent and a verdict returned, or a note saying the identity check rejected it before any credit was spent. Both marks were already on disk and going unread.

Checked against the live database, the selector goes from 85 leads to 2. The 2 are the only ones nobody has ruled on. The free collection pass is untouched and still returns its full batch of 40, which matters, because collection is the lane's actual engine and it costs nothing.

The note test is what makes this need no backfill. Records rejected on ownership carry no timestamp yet, so matching the note catches tonight's 83 immediately. A regression test locks both clauses, plus the two original guards, so a future edit cannot quietly drop them. All 8 tests pass, typecheck clean.

2. An ownership rejection is now recorded as the permanent verdict it is

src/bloodhound/verify.ts in the email repo, commit 5efd7a7.

When the identity check decides an address belongs to a stranger, that is a verdict and it does not expire: the address will not start belonging to the creator later. It now stamps the same timestamp a paid check does, so "already ruled on" is one column for any future caller instead of a note you have to know to grep. It also appends its explanation only once, which stops the 83 rows that had already collected duplicates from collecting more.

Safe to change: that timestamp is written in exactly one other place and read nowhere in either repo. Typecheck clean.

3. The sweep's cost line says which numbers are lifetime and which are this run

scripts/video-graph-sweep.ts in the finder, commit c347c21.

The line read +1366 qualified so far | 2835 llm calls | $34.1729. Three numbers, three scopes, no labels. The qualified count and the dollar figure accumulate across every session that ever ran on this book; the call count is reset every run. Divide one by the other and you get 1.2¢ a call, when this run really spent $5.44 at 0.07¢, off by a factor of seventeen.

Nothing is computed differently. The three scopes are now named in both the per-chunk line and the end-of-run summary. This is the exact class of error that produced the throughput finding withdrawn two days ago, and it cost one line to close.

4. Standing orders no longer call the recovery engine unbuilt

docs/standing-orders.md, commit a077ff9. It described needs_contact as an unbuilt lever waiting on your green light, at a pool size of 2,600. It is built, running, and the pool is 4,345. The change-log entry carries the "false means two things" trap so nobody re-opens it.

Looked at and deliberately left alone

The recovery lane's free half is the one worth tuning, and it is set conservatively. Collection costs nothing: it reads public pages, spends no credits and no LLM. It runs 40 leads every 6 hours, so 160 a day against 2,996 untouched leads, which is about 19 days to work the pool once. At the measured rate of roughly 0.3 emails found per lead, that batch feeds the paid verify pass about 48 new addresses a day, which is now exactly what verify will look at and nothing more. Raising the batch is the obvious next lever on this lane, and it is left for you because it decides how hard we hit other people's websites, which is a judgment call, not a bug.

Term invention held steady instead of tripling again. The keyword lane made 406 discovery calls for $0.95, against 337 for $1.02 yesterday. Inventing terms still costs slightly more than running them ($0.95 against $0.93), which is the ratio yesterday flagged.
