2026-08-05: the finder found, and the scorer threw it away

Nothing crashed. No quota stop, no halt flag, fatal_signatures empty for the sixth straight cycle, $0 on Anthropic. And the day still collapsed: +8 parked, down from +105. The cause was one number in one file. The scoring model was given a 2,048-token answer budget it spent on invisible reasoning, so its JSON got cut off mid-sentence and 580 of the day's 802 discovered channels (72%) were filed as scoring_failed. The finder was working the whole time.

The three questions

Q1What actually broke?

The scoring call, on a token budget that was too small to hold its own answer. The scorer runs qwen3.7-flash, a reasoning model. Its private thinking is billed and counted against the same ceiling as the visible reply, and the ceiling was 2,048. Confirmed live on real production channels: roughly 1,850 tokens went to reasoning, the JSON answer got cut mid-string, the parser reported "no JSON object found", and the channel was written to Airtable as scoring_failed with no score.

This has been latent since the 08-01 move off Anthropic to OpenRouter. The 08-04 rubric expansion did not create it, but a longer and more nuanced rubric invites more thinking, which is plausibly what tipped it over. The damage runs across two cycles: 128 rows on 08-04 plus 580 today, 733 in total. Host extraction had the identical flaw on a 600-token budget.

Fixed mid-cycle at 04:58Z by the hourly check-in agent: scoring budget 2,048 to 8,192, host budget 600 to 2,048, matching the keyword prefilter which already ran at 8,192 for this exact reason. The last full session after the fix scored 13 channels and failed on none.

Q2Why did a 72% failure rate survive 30 hours of hourly health checks?

Because the check-in was watching a number that cannot tell the two failures apart. It only ever read fresh_pitchable. Zero pitchable looks identical whether the finder found nothing or found plenty and the scorer dropped it all. So the check-in did what it was built to do for a drought: it logged 19 term_starvation observations, each asserting "term-supply wall, not a code bug", and kicked a keyword harvest that could not possibly help. Every hour, the system told itself there was nothing to fix.

The tell was sitting in the same logs. The finder's own run summaries printed Channels scored: 4 next to scoring_failed: 14, pass after pass. Nothing read that line. Yesterday's debrief also walked past it: scoring_failed: 128 was in the snapshot, buried inside the status breakdown, and the report called it a clean day.

Q3Are the 733 lost leads recoverable?

Yes, and the recovery is already running. scoring_failed rows are real prospect rows that never got a score, so nothing was deleted and the channel IDs are still held. A rescue pass (youtube-lead-finder-v1/scripts/rescore-failed.ts) started at 06:44Z: it refetches each channel from YouTube, rescores it on the fixed budget, and updates the row in place. It is naturally resumable, since it re-queries for whatever is still stuck each time it starts.

The early returns are strong, and they confirm real leads were being thrown away: of the first 56 rescored, the scores include a string of 7s and 9s across legal, clinics and coaching. Measured live 40 minutes after the cycle snapshot, scoring_failed had already fallen 580 to 572 while pitchable rose 48 to 52. At roughly 40 seconds a row the full pass takes about 8 hours.

Treat today's 48 pitchable and +8 parked as floor numbers, not a supply reading. The real yield for the day is unknown until the rescue finishes.
