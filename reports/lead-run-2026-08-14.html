The three questions

Q1Why did all 38 sessions stop for want of search terms?

Because the reserve they draw from was empty, and it was empty in a way nobody would guess from the outside. The term book holds 16,770 rows. Zero were active. The finder has two ways to refill an empty pool, and both came back with nothing:

  • Tier 1 revives terms that have never been run. That reserve drains permanently, because every term eventually gets run. It has been empty since around 08-07.
  • Tier 2 revives terms that already proved they convert and have since cooled off for 21 days. This is the one that failed, and it failed for a reason worth reading twice.

Tier 2 works in a loop: revive a term, run it once, and if it comes back all duplicates the fast-pause rule retires it again. It is then ineligible for three weeks. Run that loop hard enough for long enough and the whole reserve ends up inside its own cooling window at the same time. That is what happened. Measured this morning:

cooled 21 days, converts ≥3.5%  →    0 terms
cooled 21 days, converts ≥2%    →    0 terms
cooled 14 days, converts ≥3.5%  →   27 terms
cooled  7 days, converts ≥3.5%  →  221 terms, 20 categories, best measured at 15.2%

The oldest last-run date anywhere in the proven reserve was 18 days back, so tier 2 was arithmetically guaranteed to return zero and stay there until 08-17. Meanwhile the finder logged 19 starvation warnings and aborted in under a second, 38 times.

This is the same failure shape as the one fixed on 08-12, one level up. That fix noticed the conversion-rate bar had turned from a preference into a wall and added a lower fallback bar. The cooldown had done exactly the same thing, and nothing was watching it. Fixed today: the cooldown now relaxes too.

Q3Why did the funnel report zero emails verified?

Because the number was measuring where leads are standing right now, not what the verifier did. It counted rows whose status is exactly email_verified. Since the Postgres cutover, a verified lead moves on to ready_data_scraped within the same cycle, so it stops being counted the moment the pipeline works properly.

Today it finally hit zero: all 53 of the day's newly-parked leads had a verified email and had already moved on. The funnel read 0 verified out of 170 worth contacting, which reads exactly like the verifier broke. It didn't.

The metric now counts every status that can only be reached by verifying an email first. Recomputed against the same cycle, the figure is 53, and no other number in the snapshot changed.

What broke, what's fixed

The keyword lane spent the day inventing terms instead of using good ones

With the reserve locked out, every session fell back to the discovery loop: ask a cheap model to invent new search phrases, write them as probes, run each one once. That loop ran 64 times and it is not paying for itself any more:

The invented phrases aren't wrong, they're just landing on the same slice of YouTube the book already covers. Discovery's own dry-guard noticed and suppressed the model call 38 times, which is the guard working, but it left the sessions with nothing to run.

The 221 real terms that today's fix unlocks are measurably better than anything that loop is producing. The best of them converts at 15.2% and last ran eight days ago.

Two things worth knowing that are not faults

The 2,101 never-run terms sitting in dead are meant to be there. They were killed on purpose as consumer-intent phrasings, the kind that find people researching a career rather than people running a business. They look like a bug in the term-book counts and they are not. Do not revive them.

That works out to about 1.3 cents per lead worth contacting and 4 cents per lead parked. Cost is not a constraint on this pipeline right now.

The cooldown ladder. Tier 2 now tries four rungs and stops at the first one that yields anything: full cooldown at the preferred conversion bar, full cooldown at the fallback bar, then the shortened 7-day cooldown at each of the same two bars. Cooling is treated as worth more than the rate bar, so both rate floors are exhausted before the cooldown itself gives way. Rung 1 is unchanged, so on any day where the old code would have found terms, today's code behaves identically. Every rung below it spreads the batch across niche categories at most two apiece, which is the guard that actually stopped the 08-07 collapse when eight near-identical consultant terms landed in one pass. Set PROVEN_REVIVE_FALLBACK_COOLDOWN_DAYS to retune it. Simulated read-only against the live book before shipping: rungs 1 and 2 return nothing, rung 3 fires with 24 terms spread across 16 categories, converting between 5.6% and 15.2%.

The verified count. A shared set now defines which statuses mean an email was verified at some point: email_verified, ready_data_scraped, its legacy alias enriched, email_drafted and sent_to_smartlead. ready_no_data is deliberately left out. It is a hand-applied holding label that nothing in the pipeline writes, and counting it would mean treating a manual label as evidence the verifier ran. Eleven new test cases cover it.
