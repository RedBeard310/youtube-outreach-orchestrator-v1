The shape of the day

Yesterday was the third-biggest parking day on record, 525 leads, all of it bought from Apify at thirteen cents each. Today is the other side of that: the month's $100 allowance was already spent on day two, so the paid lane never woke up, and the free lane walked 600 leads to find two. The pool went 7,587 to 7,589.

Read on its own, +2 looks like a breakdown. It isn't. Every lane that was asked to run, ran, and none of them failed. There were no fatal signatures, no halt flag and no crashes, the twentieth consecutive day of $0 Anthropic spend, and the recovery lane's stranded count held at 3 for the twentieth day, so no selector gap has reopened. That last part is new and it is the real story of the day. The enrichment chain has been the busiest thing in this pipeline for weeks. What broke, what's fixed

1. The push hour was 43 minutes of waiting on an unclosed database connection

Fixed: youtube-email-outreach-v1 7fd02b6fd. No root access needed, no change in automator, nothing for Casey to do.

Siege writes and pushes one small batch at a time. Yesterday it ran npx tsx scripts/push-batch.ts 90 times inside the hour and sent 131 emails, which is 1.46 emails per process and about 37 seconds per process. The question is what those 37 seconds were.

Measured today, by logging every network call a push makes and when the process actually exits: a push finishes all of its real work at 1.1 seconds, then sits for 29 more seconds and exits. Loading the code is 0.78s. Asking SmartLead for the campaign's mailboxes is 0.45s, and for its sequence 0.39s. The database answers in 18 milliseconds. Nothing in the job is slow.

The 29 seconds are a leak. pipeline-db hands every caller one shared connection pool set to hold an idle connection for 30 seconds with keepalive on. Those are the right settings for a service that runs all day and the wrong ones for a script that runs for a second and quits, because the idle socket and its timer keep Node's event loop busy. The script has to close the pool to exit, and it never did. Nobody notices in a command a person types once. In a loop of 90 it is 43 minutes of an hour, which is why a one-hour limit was hit at all.

The fix is a shared runCli() wrapper that runs the command, closes the pool and preserves the exit code, now used by the push. A batch went from 31 seconds to 1.9. On yesterday's shape that turns a 57-minute push into roughly three minutes, which means the unit's one-hour limit stops being the binding constraint and raising TimeoutStartSec is no longer the thing that has to happen. Checked on all three paths: a clean run exits 0 with its full output flushed through a pipe, a refusal still prints and exits 1, a bad argument still prints and exits 1.

The same leak sits in 62 other entrypoints across the five repos. Only this one runs inside a timed loop, so only this one was costing anything, and the rest are left alone deliberately rather than churned.

2. The live send quietly dropped a setting the dry run showed, and the compiler was never pointed at the file

Fixed: same commit, with a regression test and a typecheck that now covers the directory.

The root tsconfig.json in the email repo checks src/ and tests/. It does not check scripts/, which holds 100 entrypoints, among them push-batch.ts, the last door before SmartLead and the thing Siege runs 90 times a day. So every "tsc clean" ever reported for a change under scripts/ was true and meaningless, including some in this series.

Pointing the compiler at the directory for the first time found a real one in two seconds. push-batch.ts calls addLeadToCampaign(campaign, input, settings), and that function takes two parameters, not three. The third was dropped on the floor. The setting in it is ignore_duplicate_leads_in_other_campaign, and it reached SmartLead on the dry-run preview and never on the live send, so the preview showed a request the real send didn't make.

What it would have cost, and why it hasn't yet: Siege runs one campaign per sending inbox, so a lead worked through several offers moves between campaigns, and SmartLead's default declines a lead already sitting in another one. That failure is loud, not silent, so no day has hidden one. It hasn't happened because nearly every email sent so far is a lead's first. With 7,031 leads ready and 16 offers, it was a matter of time rather than chance.

Three things shipped: the function takes the settings and sends them, a test pins the live request to match the preview exactly (it fails against the old code, which was checked both ways), and npm run typecheck:scripts now covers the directory. Twelve older scripts carry 28 pre-existing type errors; they are listed by name in the new config so the gap is visible and shrinking it is a known job, rather than hidden inside a glob. A new script has to be clean.

3. The recovery lane counted mailto links where it meant people

Fixed: youtube-outreach-orchestrator-v1 08bd8a5.

The snapshot reported 32 free email addresses beside 12 leads with new contact points, and an honest reader puts those together as 32 addresses spread across 12 leads. The truth was 32 addresses across two leads, 31 of them from one creator whose site repeats a mailto link on every page. The number that predicts parking was 2, and parking was 2.

This is the same mistake as yesterday's fix one layer down. That one separated the free lane's work from the paid lane's. This one separates addresses from people, which matters more now than it did a week ago: for the next 28 days the free pass is the only lane adding leads, so its yield is the number Casey will be reading to decide whether to fund the paid one again. An address count flatters it, because a lane finding 30 addresses on one person looks ten times healthier than a lane finding three on three.

The block now carries free_leads_with_new_email beside the address counts, and the note says plainly which one to read. Verified against the live cycle: 32 points, 2 leads, matching a hand-written query. Cross-checked against the 10-01 cycle, where the paid lane wrote one address per lead and the two counts agree at 701, which is why this only ever distorted the free lane.

What changed in how to read this pipeline. For weeks the limit was supply: find more channels, recover more addresses, research more leads. All three of those are now either finished or out of money, and what's left is 7,031 researched leads and a send path that loads 132 a day against a ramp that allows 200. The binding constraint has moved from the front of the pipeline to the back. Today's main fix is worth naming for a second reason: the hour that killed the send two days running wasn't the work being slow, it was 90 processes each waiting 29 seconds to be allowed to quit, and yesterday's report blamed startup because it counted the clock instead of measuring where the clock went.
