The three questions

Q1Why did 600 lead-slots produce one email address?

Two reasons, and only one of them is a fault.

The benign one is a picked-over book. The lane has 1,769 leads left to walk and it is on lap 19, so almost everybody it reads today it has already read eighteen times. The pass summary says this out loud: the methods found 632 things and 625 of them were already on file. Website resolution is healthy (3 leads of 150 had no site, no search refusals at all), so this is not the search plan and not a configuration fault.

The fault is underneath it. The largest single thing going wrong in the pass is a cross-domain redirect: the lead's own declared website sends us to a different domain, and the fetch refuses to read it, correctly, because otherwise we would file a stranger's contacts under this creator. That refusal was 282 of the cycle's 758 method errors, 37%, and it is rising across the day: 80, then 50, then 58, then 94.

The number looks like a web-wide problem and it is not. Nine collection methods start from the lead's website, so one refused redirect arrives in the roll-up as six separate faults under six method names. Counting back from the method that fetches the homepage once, it is about 14 leads of 150. Those 14 lose their entire page half, on every lap, for good. At four passes a day that is roughly 56 lead-slots a day spent on leads that cannot possibly produce.

Q2There was a fix for that two weeks ago. Did it work?

Nobody could tell, and the honest answer now is: almost not at all.

On 2026-11-08 a gate shipped to rescue exactly these leads. When a creator's declared link hops to another domain, it reads the page it lands on and follows the hop if the destination plainly belongs to that creator. It logged a line when it followed one and said nothing at all when it refused, so two weeks of passes could not say whether it had helped anybody, and the symptom stayed the biggest condition in the roll-up.

The gate asks two things: does the destination domain read like the creator's name, and does the page name them. Its own notes argue that a link the creator declared themselves is stronger evidence than a search result, and then it applies the identical bar a search result has to clear. That is the gap, and it is checkable. The gate's own notes name cme.sh -> www.bigdaddydigital.com as one of the hops it was built to rescue. The real lead behind that hop has channel_name "Steven Thompson", so the domain does not read like the channel at all and the hop is refused one step before the page is ever considered. The test written alongside the fix passes the channel name "Big Daddy Digital", which no lead in the database carries.

This is the common shape. A creator's branded shortener points at their firm: the channel carries the person's name and the domain carries the company's. The gate cannot see that those are the same business.

One lead still carries a sent stamp with no send behind it, standing since 2026-10-07, which is the same single lead as yesterday and not a growing gap.

Fixes shipped this cycle

The refusal that costs the most leads now names itself

The redirect gate printed a line when it followed a hop and nothing when it refused one. So the single largest fault in every pass had a symptom and no cause, and the fix meant to cure it could not be measured two weeks after it shipped.

It now records every hop it examines and which of its own three screens said no: the destination is a redirector or a link-in-bio host (working as intended, those are never the creator's site); the destination domain does not read like the creator's name (the branded-shortener case above); or the domain reads like them and the page does not name them (a parked domain, or a real miss). Each bucket keeps one untouched example, and one line prints per lead, not per method, which is the whole point. A pass footer sums it up beside the existing error roll-up it explains.

Counting changed no verdict. Nothing about which contacts get filed moved, because whether to loosen that middle screen is an ownership decision and the 2026-08-18 audit's house rule stands: nothing gets filed that cannot be tied to this creator. This measures the size of the decision instead of taking it.

The test written alongside the 11-08 fix was also corrected. It asserted that cme.sh -> www.bigdaddydigital.com is rescued using a channel name the lead does not have. The real lead's name is now a case of its own, asserting the live behaviour, so the fixture can no longer read as proof the gate works on that lead.

Verified: type check clean, both bloodhound selftests pass including the new case, and the real channel names were read out of leads.lead_candidates rather than assumed. Committed in youtube-email-outreach-v1.
