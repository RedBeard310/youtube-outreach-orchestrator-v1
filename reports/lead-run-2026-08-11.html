The three questions

Q1Why did output fall 92% overnight?

Because the pipeline was using 7 API keys when 39 were available, and it never knew. The key pool was rebuilt on 08-10, going from 9 keys to 39, with every key tested against the live API before it landed. That work went into the shared key file that all the repos are supposed to draw from.

None of them read it. The finder, the email repo and the deep-research repo each load their keys from a file inside their own folder, and those files were last written on 08-07 with 7 keys in them. So the 39 verified keys existed, worked, and reached nothing. The finder said so in its own startup line every single run: auto (7 direct keys).

This hit every way we find creators, not just one. All five of the background discovery methods live inside the finder and share its keys, which is why the drop is across the board rather than in one lane:

Q2Why did the last eight hours run one search per session?

A backend we switched off yesterday told the campaign it was out of quota, and the campaign believed it.

Here's the chain. With only 7 keys, a single pass burns through all of them in about three seconds and gets a "too many requests this minute" answer from each one. The rotation code couldn't tell that apart from "every key is permanently dead", so it gave up on the direct keys and fell through to the RapidAPI mirror, which is exactly what it's designed to do. But we retired that mirror on 08-10. It answered:

YouTube API error 429: You have exceeded the DAILY quota for Requests
on your current plan, BASIC.

That dead answer gets written to a shared status file as 100.1% of quota used. The campaign reads that file before every search and stops the whole session above 95%. So from 22:44Z, once per session, six times:

[campaign] YouTube quota at 100.1% (>= hard floor 95%) — stopping to preserve remaining credits.

There were no credits to preserve. The guard was protecting a service we'd already turned off, while the real key pool sat idle and healthy. A live test call on it succeeds today. The rate limit that started all this clears by itself in under 60 seconds; nothing needed to fail here, it needed to wait.

Q3Once the keys are fixed, is the pipeline back?

Partly. There's a second wall behind this one, and it's real. The 14 sessions that stopped for "term supply exhausted" have nothing to do with the keys. The finder ran out of things to search for.

The active search-term pool is down to 8 terms. There are no never-run terms and no rested proven terms left in reserve. Vein discovery ran 76 times and produced 0 usable new ideas against a table of 16,134 terms it has already tried. The autocomplete harvest is backed off because its seed list is mined out. All three sources of new search terms are dry at the same time, which hasn't happened before.

So the key fix restores the ability to search. It does not restore things worth searching for. Expect intake to recover tomorrow because the five sweep methods don't depend on search terms, but the keyword engine specifically will stay thin until it gets new material.

One piece of good news I checked rather than assumed: the famine did not poison the term table. Failed searches are deliberately excluded from the "this term is used up" signal, so a burst of errors can't retire a healthy term. The terms that look mined out genuinely are.

Two design details in the key fix that are worth recording, because the obvious version of it is wrong:

It merges keys by value, not by layering files. The natural approach is to load the shared file underneath the local one. That silently loses keys: the loader matches on slot names like YOUTUBE_API_KEY_1, and a stale local slot 1 wins its name and discards the bank's key sitting in that same slot. Here that would have thrown away 7 of the 39. Reading the bank separately and merging on the key values themselves keeps every distinct key from both files.

It only merges when reading the real environment. Hand the loader an explicit set of variables and it resolves exactly what you handed it. Without that rule, 9 of the finder's tests broke and one of them printed a real API key into the test output. Tests stay sealed off from the machine they run on. An unreadable bank falls back to the smaller pool and never fails a run.

Verified before commit: TypeScript clean in all four repos; 168/168 finder tests and 15/15 email-repo tests pass; the production path now resolves 39 distinct keys instead of 7 in all three repos; a live 1-unit API call on the new pool succeeds; the rate-limit fix was tested all three ways (a burst recovers, a dead pool throws in 1ms, a permanent storm gives up after a bounded 3 sweeps rather than hanging); the quota guard was tested against 5 snapshot shapes including today's real file; and campaign:dry now walks past the second search instead of stopping there.
