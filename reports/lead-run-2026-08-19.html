The three questions

Q1Was the biggest lane really IP-blocked, as it kept saying?

No, and this is the whole story of the day. The lane printed this 33 times:

[video-sweep] STOP: 20 consecutive seeds returned empty/blocked rails
              — likely IP block or dead proxy pool. Nothing consumed
              from this chunk; resuming later.

I fetched those exact seeds live, through the same proxy pool the lane uses. They came back HTTP 200, about 845KB each, carrying isShortsEligible, Sign in to confirm your age and LOGIN_REQUIRED, with exactly one distinct channel link on the page: the seed's own. Nothing was refusing us. Those videos are Shorts and age-gated uploads, and a logged-out page for one of those renders in full with no recommendation rail on it at all.

So the seeds were useless, which is fine and normal. The bug is what the lane did about it. It counted each railless page toward an outage streak, and an outage means "don't consume the seed, something is wrong with the network." After twenty of them it stopped the run without marking a single seed done. The next launch read the same state file, drew the same twenty seeds, and reached the same wall. That is a deadlock: the lane could not use those seeds and could not get past them either, and the loop happily retried every 15 minutes for nine hours.

Two facts that let this hide. The proxy pool is genuinely load-bearing here, so "proxy problem" was a plausible read: a direct fetch from this box gets HTTP 429 and a bot-check page of 3,242 bytes, while the same request through the pool gets a real page. And the lane discarded the reason for every empty page it saw, so nine hours of failure left no record of a single HTTP status. Both are fixed below.

How poisoned was that stretch of the book? Of the first 40 seeds after the restart, 34 had no rail. The frontier is sorted by view count and sits at about 2 million views, which is exactly where Shorts dominate. The lane now walks through them at two seconds each instead of stopping.

What broke

A lane that could not use a seed and could not skip it

Covered in Q1. The part worth keeping is the general shape, because it will happen again in another lane: the code had exactly two categories for a failed fetch, "worked" and "the network is against us", and a third case existed in reality. A page that renders perfectly and simply has nothing on it is a fact about the thing you asked for, not about the connection. Anything that refuses to consume a seed on failure needs to be sure which of the two it is looking at, or it will retry forever.

The health monitor graded the frozen lane "productive: true"

Yesterday's fix gave this lane its first health entry, exactly so a stall could not be silent. This morning it reported productive: true and seeds_advanced: 7,486 for a lane that had been frozen for nine hours and was still frozen while the report was being written.

Two separate errors, both fixed. The progress number was reading the chunk header, which prints the range a chunk is about to walk before any of it happens, so each of the 33 dead relaunches claimed 20 seeds it never touched. And "productive" summed the entire 24 hours, so strong work in hour one hides a dead ending, which is the case that matters most because it is still happening when you read it.

The corrected figure is 6,826 seeds, and the lane now reports idle_run_streak: 33 since 2026-08-18T22:17:56Z. That second field is the one I would have needed to see this without reading log files.

Nine hours of hammering a wall at a flat 15-minute interval

Because the failing run consumed nothing, every relaunch was identical work with an identical result: roughly 660 watch-page fetches into a dead end. It cost no money and no quota, but it is the same mistake as the 07-17 autocomplete block, where hammering a refusing endpoint kept the refusal alive. The loop now backs off 15 minutes, then 30, then 60, capped at 2 hours, and resets the moment a run gets through.

Shipped today

Four commits. Typecheck clean in both repos, 226 unit tests pass (up from 223), and every change was verified against live data or live YouTube before committing. No .env touched.

1. The video sweep can no longer deadlock on a Short finder 71fe206

A watch page is now classified rather than guessed at. A page that rendered (200KB or more, with ytInitialData) and still carries no usable rail is railless, which is a fact about the video: the seed gets consumed, counted in a new railless stat, and the lane walks on. A small body, a non-2xx, a 429 or a transport error is a refusal, which is a fact about the exit: the seed is kept and the outage streak counts it. The live bot-check page is 3,242 bytes against a real page's 800KB, so the size gap is a reliable line to draw.

Two smaller things came with it. The fetch now rotates to a different exit on a soft block, meaning a 200 that is really a consent wall, and on a non-2xx status, where before it only rotated on a 429; one poisoned exit at the front of the rotation used to be enough to condemn a seed. And it names what every exit did, which the sweep prints, along with its proxy-pool size at startup. Nine hours of failure left no evidence at all; the next outage will say what it is.

Verified live. Restarted at 07:37Z: the pool line reads rails leave via 100 rotating exits, the poisoned chunk cleared in under two minutes with all 20 seeds consumed, and the next chunk returned 91 candidate channels. 80 seeds walked in the first five minutes, against zero in the previous nine hours.

2. A blocked lane rests instead of hammering finder 71fe206

The relaunch loop backs off 15 minutes, then 30, then 60, capped at 2 hours, whenever a run stops on blocked rails or edge errors, and resets to normal the moment a run gets through. Self-clearing, so nothing needs a human. The ceiling is VIDEO_SWEEP_BLOCK_MAX_SLEEP.

3. A frozen lane can no longer report itself productive orchestrator 8c7b2b5

Seed progress is now read from a run's summary line, which only moves when seeds are actually checkpointed, instead of from the chunk header's intended range. And every lane now carries idle_run_streak and idle_since: how many of its most recent consecutive runs advanced nothing, and when that started.

This immediately surfaced something nobody had measured. Peer-network comments used to report seeds_advanced: null, which reads as "unknown". It now reads 0 across six runs, idle since 09:28Z yesterday, which is the truth: its book is finished.

4. Measure how many recommended-feed seeds are just Shorts finder 8420568

That lane walks each seed's latest upload, and if the latest upload is a Short there is no rail, so the seed is spent for nothing. Its per-seed yield has halved four laps running and nobody has checked how much of that is simply Shorts rather than genuine exhaustion. This counts it and changes nothing else. If the number comes back large, the fix is free: the RSS feed already carries the 15 most recent uploads, so a railless latest video can fall back to the previous one at zero quota.
