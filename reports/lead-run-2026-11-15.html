The shape of the day

Four normal days at ten to twelve ticks each, then the cliff inside 11-12: the last run log is 08:21:48Z that morning and the first refusal is 10:20Z. Every tick since has exited on the same line, could not read the Apify monthly ledger, and exited 0, so systemd reports success every two hours.

The three questions

Q1Why did two reports miss a dead lane?

Because the refusal left no trace in the one place this report looks.

The 2026-11-02 note on that block rests on a sentence that was true when it was written: a tick that scrapes nothing still writes a run log. That only holds for a tick which gets as far as the batch. The halt flag, a live batch, the lock, a missing token and an unreadable ledger all exited before anything reached disk, and the one remaining exit, resting under the minimum batch size, was the only one that left a stamp. So the newest run log stayed at 2026-11-12T08:21:48Z and the reader went on publishing its answer: candidate_pool_dry: true, a 34-tick dry streak, $31.06 left, binding_constraint: candidate_supply.

Yesterday’s lane table printed “No. It finished its book; the shortage is candidates” about a lane that had not asked the question since Thursday. The 11-13 snapshot still had one real log inside its window, so that morning was honest; 11-14 was the first stale one and today’s would have been the second.

The cost: 71.6 hours of a paid lane doing nothing, with $31.06 of the November allowance on the books, $21.06 of it spendable, against a billing cycle that closes 2026-11-30. At the measured per-run price that is roughly 300 channels it will not get to.

Q2What happened to the one creator who said yes?

He reached Casey with a drafted reply. What the machine cannot do is send it.

danielwangwe7@gmail.com was read simple-yes/high at 19:40:01Z and 28 more times over the next seven hours, once per classifier pass. At 02:23:40Z the run closed escalated 1 with the hold cannot tell which mailbox this thread sends from, so cannot sign it, and every run after that read 0 replies.

One correction to yesterday’s framing. That report described these yeses as sitting in a queue, because the pause normally leaves a reply unprocessed. The escalation is the exception: it marks the reply processed and writes a row into automator/state/escalations.jsonl, which is why the queue dropped to 0 and stayed there. Across the whole file, 16 people have been escalated with this hold since 2026-09-27 and 15 of those escalations carry a drafted reply. They are in the approval queue, not lost.

The cause is named in the code rather than inferred here. The comment above the check in scripts/smartlead-auto-reply.py reads: “The usual cause is a thread whose mailbox has since been deleted, which is also a thread SmartLead could not reply through anyway.” SmartLead threads a reply through the same mailbox that sent the original, so once that mailbox is gone there is no address to sign as and no route to answer on. With 37 mailboxes in the stopped band this morning and 71 paused by the older gate over its lifetime, a warm reply landing on a mailbox that no longer exists will keep happening.

The hold has fired 12 times since 2026-09-27 across 11 people, and every single one was simple-yes/high. Yesterday’s report put it at 11 since 10-07 with 8 of them a yes; the first was 09-27 and the share is all of them.

Fixes shipped this cycle

1. Every Apify tick leaves a stamp, including one that refuses

youtube-email-outreach-v1, scripts/apify-endspec-loop.sh. All six early exits and the batch launch now write logs/apify-endspec-tick.json: 

{"at":"2026-11-15T08:20:54Z","outcome":"skipped","reason":"could not read the Apify monthly ledger"}

One line, written before the exit, never a reason the tick fails. It is the difference between “asked and got no” and “never asked”, which is exactly what three days of this outage turned into a published number. Syntax-checked, and the emitted line parses as JSON. The auto-sync timer committed it under its own message (b7e71c4aa) before the autopilot-improve: commit could land, so the change is on the branch and will push; the message is the timer’s.

2. A silent lane now says so, instead of repeating last week’s answer

youtube-outreach-orchestrator-v1 a888e20 and d490973. recovery_budget.apify gained lane_answered_in_cycle, which is whether any run log falls inside the window, the only evidence the lane got as far as counting candidates. When it is false:

  • candidate_pool_dry reads null, not true. Unknown, and not a finished book.
  • projection.binding_constraint reads lane_silent and projected_leads is null, because neither money nor supply is the wall when nobody asked.
  • candidate_dry_streak and candidate_dry_since stay, because they are real history up to that last log, now read beside lane_silent_hours.

Also published: newest_run_log_at, lane_silent_hours (71.6 this morning) and lane_last_tick_at / _outcome / _reason off the new stamp. Verified against the live files before committing. Two new selftest assertions, typecheck clean.

3. The report generator is typechecked, and it was hiding a real defect

youtube-outreach-orchestrator-v1 be584a4. Yesterday’s report found that tsconfig.json included only src/**, so npm run typecheck had never read scripts/autopilot/, the directory that generates the metrics this whole series is grounded in. It left the three pre-existing errors for a deliberate pass. This was the quiet cycle for it.

One of the three was not cosmetic. bandGateFacts() builds the band gate’s per-mailbox reason ledger and then left it out of its success return; only the blank early return carried it. The caller does inboxGateFacts(gateState, band.reasons), so on every real run that argument was undefined and fell back to the empty default. The band gate adopts health-only pauses out of the old gate’s registry and deletes them there, so for those mailboxes its ledger is the only place the reason still exists, and the last fallback in the health/warmup split never fired. A pause explained only by the band gate counted as gate_paused_unexplained, which is the one answer the 2026-10-15 split was built so it could never give.

It cost nothing this cycle, because gate_paused was 0, and would cost a wrong reason on any cycle where the older gate pulls a mailbox the band gate has already adopted. The other two were declaration-level: a fixture array inferring as never[], and siegePushOutcome promising three lost_split_* fields it does not set itself. Both now say what they mean. Nineteen new selftest assertions this cycle, all passing.
