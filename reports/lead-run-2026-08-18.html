The three questions

Q1Why did keyword search suddenly find seven times more channels than yesterday?

It didn't. It found 223, which is roughly what it has found all week. The other 3,279 belong to video-graph-sweep, the video-level sweep that shipped yesterday morning at 10:40Z.

Every lane tags the rows it writes, and discovery-method.ts reads that tag to decide which lane gets the credit. The tags it knew about were graph:, peer-comment:, peer-guest:, comment: and podcast:. The new lane writes video-graph:. That matches none of them, and the final line of the function hands anything unmatched to the keyword engine.

So the new lane's entire output was filed under the one lane we have been calling starved. Reading yesterday's numbers at face value, the obvious conclusion was that the keyword harvest had recovered on its own and the term-supply problem had solved itself. It hasn't. The keyword engine hard-stopped on term_supply_exhausted in 33 of 33 sessions, which is the same starvation as always, just hidden behind someone else's leads.

The second consequence is worse than the mislabelled report. The same function decides what counts as a finder pass's own yield. It was written on 2026-08-10 for exactly this reason: sweep daemons write into the lead base continuously, and a pass measures itself by diffing that base, so every daemon row landing mid-pass gets counted as the pass's own work. Because video-graph: read as keyword engine, the video sweep's rows were once again inflating the finder's per-pass yield, and that number feeds the fade detector that decides when to pivot a mined-out term slice. The bug the file exists to prevent came back through the door it left open.

Q2Did yesterday's key-rotation fix hold?

Yes, and by more than expected. YouTube rate limits went from 411 last cycle to 4 this one.

The fix moved the list of spent keys out of process memory and onto disk, and made rotation open at a spread offset instead of always at key #1. Both halves are visibly working. logs/youtube-dead-keys.json now holds five quota-dead keys, each recorded as a truncated hash rather than a key value, each set to expire at 2026-08-19T07:00Z — midnight Pacific, which is when Google actually resets the quota.

Zero quota stops, and no key was suspended. Five keys dead out of a pool of 52 means the pool is still nowhere near the constraint.

Q3Is the re-walking lane still worth what it costs?

Yes, but the per-seed decline continued exactly as predicted. Lap 4 of the recommended-videos book finished this cycle: 9,701 seeds, 315 good leads, $6.26.

Per-seed yield by lap: 0.453 → 0.373 → 0.053 → 0.032. Yesterday's debrief forecast 0.025 for this lap, so the decay is tracking. Per lead it is still 2.0¢, second-cheapest of anything we run, because cost follows channels scored rather than seeds walked and a re-walk drops most of what it sees for free.

The 25¢-per-lead gate approved this lap without hesitation and will keep approving laps 5, 6 and 7 while each returns roughly half the last. That decision is still open and still Casey's — it is a question of how long to keep a decaying lane alive, not a bug. Nothing was changed.

What broke

A new lane could ship without the report knowing

This is the part worth fixing rather than the mislabelling itself. The classifier's closing rule was written as a deliberate fail-safe: anything unrecognised counts as the keyword engine, on the reasoning that over-counting is survivable and a false zero would make every pass look like a fade and send the campaign into permanent discovery churn.

That reasoning is sound for the cases it names — a renamed field, a blanked value, a new writer that emits no tag at all. All three produce an empty or untagged value. It is wrong for the case that actually happened, which was a new writer that emits a perfectly good tag nobody had registered. There the fail-safe doesn't degrade quietly; it hands one lane's entire output to another and reports it with total confidence.

33 of 33 sessions stopped for want of terms

Every campaign session this cycle ended on term_supply_exhausted, up from 19 of 21. Standing orders demoted the keyword lane to opportunistic on 08-14 and say not to treat an empty term pool as an incident, so this is not a regression in itself.

What is new is that today it was invisible. The keyword lane looked like the day's second-biggest producer while it was in fact stopping instantly in every single session. The lane still posts a respectable 5.83% hit rate and the cheapest leads we have at 1.5¢. It has had no new seed phrases since 07-13.

Podcast crossover produced nothing again

It has a timer, it ran once, and it wrote zero channels and zero leads this cycle. That is three cycles at or near zero. Either it needs its data source connected or the timer should come off. Left alone, since switching it off is a call about a lane Casey built deliberately.

Shipped today

youtube-outreach-orchestrator-v1 094d108 — a new lane can no longer hide inside keyword search

One commit, one file plus its caller. Typecheck clean. Verified against an eleven-case table covering every tag in live use, then verified end to end by re-running the metrics collector over today's real data.

Three changes. First, video-graph: is registered as its own lane, so it appears in the report by name and stops inflating the finder's per-pass yield.

Second, and this is the durable half: a row carrying a daemon-shaped tag is never the keyword engine, whether or not the classifier has heard of the daemon. A daemon tag is a lowercase hyphenated word followed immediately by a colon. Checked against 15,578 genuine keyword rows from the past month, exactly zero match that shape, so it cannot mistake a real search term for a lane tag.

Third, an unregistered lane now reports under its own prefix — unregistered:video-graph — instead of being absorbed. The next lane that ships without being registered will name itself in the next morning's debrief rather than spending a day disguised as something else.

The original fail-safe is intact. Null values and untagged terms still resolve to the keyword engine, so every failure mode the old comment guarded against behaves exactly as it did.
