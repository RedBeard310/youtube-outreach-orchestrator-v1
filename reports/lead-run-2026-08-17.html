Q3What is the key pool costing us to use?

Counted from the warnings in the cycle's 21 session logs. This has been true every day this month and nothing in the pipeline reports it, because every symptom is a line that reads as routine.

The pool holds 52 direct YouTube keys. Here is how many separate processes found each slot already spent, and how many bounced off it on a per-minute limit:

spent         8   58  161  204  204  199  ...  16    9    3     0

The good news first, because it is the bigger fact. No process ran out of keys all cycle, and no key was suspended. Slots 3 to 20 drained their daily allowance and slots 21 to 52 were never needed. So a full day of this pipeline costs roughly 20 keys' worth of quota, and the 32 keys behind that are real headroom in reserve. The pool is not the constraint, and the accounts Casey has been adding are genuine spare capacity.

What it cost to get there is the problem. Two faults, one root. The key-handling code kept its list of spent keys in memory, and its own comment said "production runs one client per run." That was true once. This cycle ran 259 finder passes plus four always-on sweep services, so a couple of hundred short-lived processes each started with a blank list and each rediscovered the spent keys the same way, by spending a request on one. That is the 2,091 quota-exhausted responses, and why slots 4 and 5 appear 204 times each, roughly once per process that ran.

Second, every process opened rotation at slot 1, so the whole fleet's opening burst landed on the same three keys. 403 of the cycle's 411 per-minute rate limits hit slots 1, 2 and 3, and the second row above shows how sharply it stops: slot 4 and everything past it took none. Those front keys are alive and healthy. They are simply being asked by twenty-one sessions at once, so processes bounce off them into the drained middle of the pool before reaching a key that will answer.

So the bill is about twenty wasted round trips at the front of every process, plus a standing rate-limit collision on three keys that is pure self-inflicted latency. Nothing failed and no cycle was ever logged as quota-stopped, which is exactly why it lasted a month. Both halves are fixed today, see below.

1. A spent key stays spent, across processes, until Google says otherwise

New src/youtube/dead-keys.ts holds the spent-key list on disk instead of in one process's memory, so the next of the day's few hundred processes skips a dead key without spending a request. Each entry carries its own expiry, because "dead" is not permanent: a daily-quota death expires at the next midnight Pacific, which is when Google actually resets, and a project suspension holds for 48 hours because it needs a human appeal. A per-minute rate limit is never recorded at all.

Keys are stored as a truncated SHA-256, never the value, so the file is safe to sit in logs/ and safe to read out loud. Verified on disk: a quota death writes expires_at: 2026-08-18T07:00:00Z, the file contains no trace of the key, and a second process skips it with zero requests.

One guard matters more than the rest. If the remembered state ever claims the whole pool is dead, it is thrown away and the pool is re-probed. A run that trusted a bad state file would die before issuing a single request, and in auto mode it would try to fall through to the retired RapidAPI mirror on the way down. Being wrong there costs a whole run; re-probing costs one sweep.

2. The fleet no longer all opens on key #1

Rotation now starts at a spread offset. Verified against the real pool: 60 client constructions landed on 36 distinct slots spanning #1 to #51, where before all 60 would have opened on #1. Total capacity is unchanged, and the point is not to reach the spare keys, which were always reachable. The point is that 21 sessions stop arriving at the same three keys in the same second, which is where 403 of the cycle's 411 rate limits came from.

Injecting a fetch opts out of both changes, so tests and fixture captures stay hermetic and never read or write the live state file. The house rules are kept: no key count is hard-coded anywhere, and the pool size is whatever the environment holds.

A note found on the way past, unrelated but worth recording: mkdirSync with recursive: true against an unwritable prefix spins forever on this kernel rather than raising. It is why a test hung for five minutes. The code now checks the directory is absent before creating it.

3. Written down so it does not come back

The orchestrator's CLAUDE.md key-pool section now carries the rule in one line: a run is not a process. Key deaths belong on disk with an expiry, and rotation must never open at index 0. The old assumption was documented as correct for two months, which is why it survived.
