Fixes shipped this cycle

1. The follow-up count this report sizes the fleet with stopped sizing the fleet on 10-13

b11a3be, youtube-outreach-orchestrator-v1

Q2 is the whole story. The send block published followups_due and told the reader, in its own note, to size the fleet with it. Siege had stopped using that count five weeks earlier. On Tuesday it read 0 on all 124 mailboxes beside 620 people mid-sequence, which under the old rule turns a full queue into 450 wasted slots.

Six new fields publish what Siege really subtracts: queued_firsts, mid_sequence, followups_reserved, queue_load, followups_rate with its source, and slots_explained. The rate comes out of automator/config/siege.json so a change there follows without an edit here, and anything unreadable degrades to the documented 0.5.

slots_explained is the guard on the whole story. It checks, mailbox by mailbox, that capacity minus the load reproduces Siege’s own slot count. True means a reader may subtract; false means automator changed the formula, so quote mailbox_slots and derive nothing. It reads true on the 11-13, 11-16 and 11-17 plans. And missing means unknown, not empty: a plan that stops carrying the queue keys nulls the derived fields rather than publishing a load of zero, because a zero load makes an occupied fleet look idle, which is the fault being fixed.

Verified against the three real plan files, which reproduce 184, 247 and 315 slots exactly. Nine new assertions, selftest all-pass, typecheck clean.

2. Six mornings of hand-probing Apify, because one refusal covered four different repairs

9f5b76c4d, youtube-email-outreach-v1

The ledger read in scripts/apify-endspec-loop.sh had one failure message, “could not read the Apify monthly ledger”, for a rejected token, an unreachable Apify, a server error and a changed response shape. Those are four different repairs: an operator replacing a credential, nothing, waiting, and an edit to that file. The lane has refused on that line since 2026-11-12 and every morning since has probed /v2/users/me/limits by hand to learn it is HTTP 401.

The status and Apify’s own error type now go into the refusal, so the stamp a reader opens first says Apify rejected the token (HTTP 401 user-or-token-not-found). Apify’s prose is dropped and only the type kept: the message can carry an account name, and varying text would break the since/consecutive counter that sizes an outage.

Six response shapes exercised against the real parser (401, unreachable, 429, 500, a healthy 200 that returns $31.06 and matches the known allowance, and a 200 in an unreadable shape), then the live script run end to end: new line logged, new stamp written, exit 0.
