The three questions

Q1Did yesterday's Shorts fix actually hold?

Yes, decisively. The lane that spent nine hours retrying twenty unusable seeds walked 5,718 seeds today and finished as the pipeline's biggest producer. Its idle-run streak is 0. The new railless counter, which records a watch page that loaded perfectly and simply has no recommendation rail on it, sits at 88, so the failure class is real and the lane now consumes those seeds and walks on instead of deadlocking on them.

It also produced the best lead rate of any lane, 8.1%, against 6.3% for the recommended-videos feed and 3.6% for keyword search. Yesterday's worry that the remaining book was heavily Shorts and therefore thinner than it looked did not play out: 88 railless pages in 5,718 seeds is 1.5%.

Q2What happens to that lane tomorrow?

It stops, permanently, and nothing restarts it. The book is 13,784 of 16,718 walked, so 2,934 seeds remain against a demonstrated 5,718 a day. It finishes some time this evening. When it does, its loop exits 0 on purpose, and the service is set to restart only on failure, so a clean finish is the one thing that keeps it down for good.

Both other sweeps have an hourly keep-alive that tops their book up. This one had none. When I went to install it I found the refill it would call was broken in two more ways:

① Its seed query has never worked. It selects c.channel_name from enrichment.channels, a column that table has never had. Every run died on column does not exist and wrote an empty seed file, and the shell script then aborted on its own empty-output guard. The lane's refill has been failing safe and silent since it was written.

② Even fixed, it deleted the lane's memory. The old script removed the state file so the new seed list took effect, which threw away both the walked-seed list and the lifetime stats. Of the 14,993 seeds the fixed query returns, 9,743 are already walked and only 2,949 are new ground. A refresh would have spent roughly two days re-fetching rails it had already seen.

All three fixed and installed today. Details below.

Q3Is the lane health monitor telling the truth yet?

No. Yesterday it called a frozen lane productive; today it called a working lane dead. Peer-network comments reported productive: false, seeds_advanced: 0, idle_run_streak: 5. It actually walked about 405 seeds this cycle and produced 755 channels and 13 good leads.

The cause is a split between where the work happens and where the monitor looks. peer-sweep.ts --extend does not only extend the book, it walks the new seeds in the same process, inside the refill script. The refill then restarts the sweep service, which finds an empty book and writes a fifteen-line log saying 10,182 seeds total | 10,182 done | 0 remaining. The monitor grades the lane off that directory, so it saw only the no-op and never the walk, which went to the system journal.

This matters more than one wrong field. A monitor that reports a healthy lane as idle every single cycle cannot flag the cycle a lane genuinely stalls, which is exactly what it was built for two days ago.

Shipped today

One commit in the finder, e44989f. Every change verified against live data or a copy of live state before committing. Nothing in any .env.

1. The biggest lane can no longer go dormant when its book drains

Three fixes that only work together:

  • The seed query runs at all now. c.channel_name became c.channel_title. It returns 14,993 seeds.
  • The refresh merges instead of resetting. It keeps the walked-seed list and the lifetime stats, adds only genuinely new seeds, upgrades old seed rows that were missing the channel name, and re-sorts the book by view count ascending, which is the policy the query encodes. Verified against a copy of live state: 16,718 seeds became 19,667, the walked list and stats survived intact, and seeds remaining went from 2,934 to 5,883.
  • A timer runs it. Hourly at :30, off the half hour so it does not collide with the other two refills. Installed, enabled and smoke-tested: while the sweep is running the tick exits in a second with sweep still running — skipping.

Written to be re-run safely on any schedule. It no-ops while the sweep is live, it holds the sweep's own lock, and a failed merge leaves state untouched rather than half-written.

2. A working lane can no longer report itself idle

The peer-sweep refill now writes its own output into the session directory the health monitor reads. Verified by running the monitor's parser over the real journal output of the 05:35Z run: it reads 75 seeds advanced, where before it read 0.
