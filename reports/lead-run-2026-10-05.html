The shape of the day

On the surface this is the third quiet weekend cycle in a row. Discovery stayed off by order, for the twelfth debrief. The enrichment chain ran one batch, did one lead and went idle, that lead being the only new work in existence. The paid Apify lane stayed asleep on $0 spendable and will until 31 October. Nothing was emailed, because siege-plan.timer runs Monday to Friday and this cycle was Sunday. No fatal signatures, no halt, no crashes, and a twenty-second straight day of $0 Anthropic spend.

The free recovery pass walked 600 leads across four passes and found contact details for 11 people, of which 2 were email addresses. One of those two verified clean and flipped, and that single lead is the whole of the +1.

Underneath that, something did break, and it broke mid-cycle. The lane's site-resolution rate across its four passes went 4%, 85%, 91%, 90%. Yesterday's report put 1.6% on its front page and called resolution healthy. The hourly check-in noticed every bit of this and alarmed correctly, once per pass, at 17:11Z, 00:11Z and 06:11Z. All three alarms recorded the same verdict: attributed_to: "unexplained", with zero Brave key refusals inside the pass, and the advice "check the collect log before spending anything".

The collect log could not answer, which is the part worth fixing. Both of those facts, a 90% no-site rate and no key refusal, are also exactly what a picked-over book looks like, and the pipeline had no way to tell the two apart. Chasing it down produced a cause that was not on anybody's list.

What broke, what's fixed

1. Website resolution in the recovery lane was off, and had no way to say so

Fixed: youtube-email-outreach-v1 27dbbb246. One spending consequence for Casey, below.

Nine of the recovery lane's thirteen collection methods start from the creator's own website. The lane gets that website one of two ways: it reads one already on file, or it asks Brave Search. Reading what's on file is free, so the lane prefers it, and that is why the numbers looked fine for weeks. The cursor was walking through leads that already had a stored site. Yesterday 588 of 600 did.

This cycle the cursor moved into the part of the book that doesn't, and the second route turned out not to exist. Measured through the collect pass's real import graph, braveKeys() returned 0. The keys are in the shared env bank as BRAVE_SEARCH_API_KEY_1 and _2, and nothing in the chain that runs the lane loads that bank: recovery-lane.service sets only HOME and PATH, run-recovery.ts reads the orchestrator's own .env, which has no BRAVE_ name in it, and the collect child inherits that same empty environment.

So the search function returned an empty list on its first line, before making any request. No request means no failure, no failure means no 402, and no 402 means the loud warning added on 2026-09-04 for exactly this symptom was unreachable. The caller reads an empty result as "this creator has no findable website" and skips nine methods. That is the 09-04 outage again, arriving through configuration instead of billing, and it is the "repo .env shadows the shared bank" failure class the shared-env loader was written to end. The loader was never wired into this entry point.

Two changes. The CLI now loads the shared bank as its first import, which is the house pattern and the reason src/load-shared-env.ts exists. And an unconfigured key pool now counts itself and says so once, in plain words, instead of returning quietly.

Verified end to end on one real site-less lead from the collapsed pass, dry run, nothing written: the keys load (2, up from 0), Brave is called, it answers 200, and the new per-pass line reports what happened. Typecheck clean on both repos.

What this costs. Each unresolved lead is one Brave search at $5 per 1,000. At this cycle's rate that's about 405 searches a cycle, roughly $2 a day, against key _1's funded cap. Key _1 answered 200 today, so it has room; key _2 is still refusing at its $5 cap. The plan's own monthly limit is the hard stop, so there is no runaway here, but this does start spending where yesterday it spent nothing. The spend is restoring designed behaviour, not new behaviour, and it is Casey's to reverse.

What it does not promise. The lane will now actually look. Whether these particular creators have findable sites is unknown, and the one lead probed today did not. Expect the no-site rate to fall; do not expect a yield jump until a full pass measures one.

2. An empty search result had three causes and the log could name only one

Fixed: same commit.

The 09-04 fix made a spent plan loud, and that half works. Everything else that ends in an empty result stayed silent, and all of it is indistinguishable from a creator with no website:

One, every key refused, which has been loud since 09-04. Two, an error that isn't a key refusal: a 5xx from Brave, a malformed reply, a parse failure. Three, Brave answered perfectly well and all five hits were social profiles or directory sites, which is a real and benign answer. Two is a fault and three is a picked-over book, and they produced the same silence.

All four outcomes are now counted, and every collect pass prints one line saying which it was. The first non-refusal error also names itself once. Counting calls nothing and costs nothing. Today's probe pass printed 1 searches, 0 resolved a candidate site, 1 answered with only social/third-party hits, 0 hit a key refusal, 0 errored, which is the sentence that would have turned three unexplained alarms into a diagnosis on the first one.

Fixed: youtube-outreach-orchestrator-v1 3870e9e. Nothing for Casey to do.

The check-in has measured the no-site rate since 09-04 and alarmed on it correctly. None of it reached the daily snapshot. fatal_signatures_today stays empty because these are observations rather than crashes, so a reader working only from the authoritative file saw a quiet +1 day and nothing else. The rate had to be hand-counted out of the collect log on two cycles running, which is the manual step the 09-04 incident was supposed to end.

recovery_lane.site_resolution now carries the newest completed pass: the rate, the sample, how much of it was a re-walk, how many key refusals happened inside the pass, how many resolved leads yielded anything, and a collapsed flag set from the check-in's own 70% threshold rather than a second invented bar. It reads the pass with the same function the alarm uses. Three separate re-implementations of that pass boundary have already gone wrong, on 09-13, 09-22 and 09-28, and a fourth here would be the worst place for one: it would let the report and the alarm disagree about the same pass.

Verified against the live log: 135 of 150, 90%, collapsed: true, matching the 06:11Z alarm record field for field.

What changed in how to read this pipeline. For three cycles the lesson has been the same: the machine runs, and what needs repair is the instrument reading it. Today that lesson arrived with teeth. A number on yesterday's front page, 1.6% of leads with no website, read as proof of health. It was measuring a stretch of the book where the data was already stored, over a search route that had been dead the whole time. The alarm worked, fired three times, and labelled the cause unexplained, because the only failure it could name was a spent plan and the plan was never asked. A silent code path and a healthy reading look the same until the day the work depends on it. Four of the measures this report leans on, the no-site rate, the already-sent count, the Brave outcome, and the chain log, could not be read from the snapshot two days ago. All four can be now.
