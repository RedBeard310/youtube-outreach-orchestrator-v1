That is the documented weekend effect: every offer is a three-email sequence on days 0, 4 and 10, SmartLead sends Monday to Thursday, so a weekend of due follow-ups lands on Monday on top of Monday’s own.

Then Siege filled those 247 slots by tier. The waiting queue is 485 whale, 650 strong7 and 25 other7, and the whale tier ran out of never-emailed people back on 2026-10-13, so its re-offer queue takes the slots while lower tiers wait. Fixes shipped this cycle

Three, all in the same place: a published zero that could mean three different things, an outage gauge that could not remember, and a baseline carried by one day.

1. Four zeros could not tell an idle enrichment chain from a frozen one

youtube-outreach-orchestrator-v1 86efc81. The enrichment block published batches: 0, leads_done: 0, leads_failed: 0, in_flight: 0, which is the honest answer for a quiet trickle, for a chain frozen on a gate, and for a chain that is not running at all. Three different mornings, one published shape.

It had already cost two. The chain hit openrouter account out of credits (DRY 0.94 1.00) at 2026-11-12T05:43:13Z and did not clear until 2026-11-14T00:59:58Z. Forty-three hours frozen, spanning two whole cycles that each published those same four zeros. Nothing generated saw it, because openrouter_today reads the finder’s spend log and the finder is paused, so that block printed a balance and five figures of runway beside an account past zero. The chain had been saying it in plain words in its own log the whole time.

A new enrichmentChainState() reads the chain’s newest state and publishes it beside the counters: chain_state, chain_blocked, chain_blocked_since, chain_blocked_hours, chain_silent_hours and log_found. Blocked means a gate (no credit, no transcripts, no YouTube quota, a cool-down) or a state that exits the process (the halt flag, the hard wall).

Two details that matter. A restart is transparent: the chain re-execs itself when its script changes on disk and systemd restarts it besides, so a restart inside a gate is ordinary, and counting it as a state ended the gate’s run and reset the clock. Reading it that way published 1.5 hours for a freeze then 26 hours old. And the matcher for the halt flag is anchored to the chain’s exact wording, because a once-a-day note in the same log says halt.flag exists and is NOT the halt flag, nothing is halted, and a looser match reads that note as an outage.

Verified against the live chain log at three real cycle boundaries: the 11-13 close now reports gate_openrouter_credits blocked for 26.3 hours where it published four zeros, and this cycle correctly reports idling_no_inflow, not blocked. Seven new assertions, typecheck clean, whole selftest passing.

2. A stamp cannot remember an outage older than itself

youtube-outreach-orchestrator-v1 a8fc221. One new field, lane_no_work_hours: the age of the newest Apify run log. A tick only writes a run log when it reaches a batch, so that age is exactly how long the lane has done no work. It needs no stamp, no threshold and no judgement about which exit path ran.

On today’s files it reads 119.6 where lane_refusing_hours read 23.6. The block note now says to quote it whenever the two disagree, because the stamp only ever covers the part of an outage it witnessed.

It is deliberately not called refusing-hours. A lane can be quiet without refusing, and the two differ here by the gap between the last good run at 08:21:48Z and the first journal refusal at 10:20Z. So 119.6 brackets a refusal run of about 117.7 hours. Two hours of slack, stated in the note, is the better error than a gauge reading 23.6.

A first attempt tried to flag the stamp as incomplete by comparing the newest run log against the stamp’s start, and a selftest killed it: that comparison cannot tell a four-day gap from a one-tick gap, so it would have flagged every honest outage too. The field that shipped makes no such judgement.

3. A week carried by one day read as a steady week

youtube-outreach-orchestrator-v1 a7fbf70, src/db.ts. first_touch_pct_prev_7d is the baseline every morning compares against, and it is a ratio over a whole week, so one big day sets it for the next seven. This cycle it published 0.4% against 21.4%, which says today collapsed off a healthy week.

The new first_touch_by_day publishes the series instead, oldest first, buckets by each person’s own earliest send so it cannot disagree with first_touch one level up, and fills a day that reached nobody in as a 0 rather than leaving it out, because a gap a reader has to notice is how a slide reads as noise.
